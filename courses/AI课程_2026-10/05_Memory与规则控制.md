# 第 5 课 · Memory 与规则控制：让 AI 每次都按规矩来

> 目标：会写规则文件、会管理记忆、知道哪些规则该写进提示词、哪些必须交给 Hook / 权限强制执行。
> 本课大量案例来自 ThinkNova 自己的记忆库（`MEMORY.md` + 100 多个主题文件）——这是我们踩坑踩出来的体系。

---

## 5.1 规则控制的四层强度

从「建议」到「强制」：

| 强度 | 手段 | 模型能违反吗 | 适合放什么 |
|---|---|---|---|
| ① 弱 | 对话里说一句 | 很容易（下次会话就忘） | 一次性要求 |
| ② 中 | 规则文件 `CLAUDE.md` / `AGENTS.md`、记忆 | 可能（太长、冲突、被稀释时） | 项目约定、风格、流程 |
| ③ 强 | Skill（按场景加载的标准流程） | 较难（流程明确） | 有固定步骤的专业活 |
| ④ 硬 | **权限配置 + Hooks + 沙箱** | **不能**（Harness 层拦截） | 安全红线、不可逆操作 |

> 🔴 **核心原则**：**凡是「违反一次就出事故」的规则，不要只写在提示词里，要落到第 ④ 层。**
> 例：「不许删生产数据」→ 权限 deny；「每次改完跑格式化」→ PostToolUse Hook；「密钥不外发」→ Hook 扫描 + 沙箱网络限制。

## 5.2 规则文件怎么写（CLAUDE.md / AGENTS.md 通用）

### 标准结构模板

```markdown
# 项目名

## 这是什么
一两句话：项目做什么、技术栈。

## 常用命令
- 安装：npm install
- 测试：npm test -- <文件>
- 构建 / 检查：npm run lint && npm run typecheck

## 代码约定
- 用 TypeScript strict；组件放 src/components/
- 提交前必须测试通过

## 红线（违反 = 返工）
- 不改 migrations/ 下已发布的文件
- 线上 config 只改文本字段，结构变更交技术

## 先读哪个文件
| 要做什么 | 先开 |
|---|---|
| 改提示词 | docs/prompt_rules.md |
| 发布 | scripts/publish/README.md |
```

### 写好规则的 8 条原则（ThinkNova 实战提炼）

1. **短**：规则文件每次都进上下文，每一行都在消耗注意力。ThinkNova 的 `MEMORY.md` 定了「超 17KB 当场瘦身」。
2. **索引 + 下沉**：主文件只放「一条一行 + 指向详细文件的链接」，细节放子文件按需读（这就是手工版的渐进式披露）。
3. **按触发时机分层**：「每次开口前」「改配置前」「验收时」「汇报时」分开写，模型在对应时机才想得起来。
4. **写 WHAT + DONE，不写空话**：
   - ❌「要认真核对」
   - ✅「改完必须烧一单，拉该单真实提交串，看见新文案才算完成」
5. **指派式 > 禁令式**：
   - ❌「绝不要拍空镜」
   - ✅「第 1 格拍店员手部动作，第 2 格拍产品微距」
   - 必须禁止时，禁令后**立刻跟替换项**：「不说轮廓，说形状或线条」
   - ThinkNova 实测：同一目标只把禁令改成指派，结果从全败翻成全胜。
6. **数量给硬配额**：「五格里至少三格是户外实景」比「尽量多拍户外」有效。
7. **每条规则带「为什么」**：模型知道原因，遇到规则没覆盖的情况才能正确推断。
8. **规则不能互相打架**：加一条前先问「它挤掉谁、和谁冲突」。ThinkNova 事故：同一提示词里「每格写满 90 字」和「总字数不超过 900 字」打架，导致一半订单要重试。

## 5.3 记忆管理：只留现状，不堆历史

### 自动记忆的结构（以 Claude Code auto memory 为例，本仓库即实例）

```
memory/
├── MEMORY.md                 ← 索引：每次会话自动加载，必须短
├── user_profile.md           ← 用户是谁、沟通偏好
├── feedback_xxx.md           ← 用户纠正过的做法（「下次别这样」）
├── project_xxx.md            ← 项目当前状态
└── reference_xxx.md          ← 查询手册（路径、接口、字段）
```

每个文件头部写 `name` / `description`（**description 写触发时机**：「要改提示词之前 → 先看这里」），这样模型在对的时机才会去读。

### 记忆的五条铁律

| 铁律 | 反面事故（真实发生过） |
|---|---|
| **新结论写入前，先搜同主题旧结论，旧的当场删或标作废** | 新旧结论并存，AI 读到旧的就照着答，一天栽三次 |
| **作废标必须写清三件：作废什么、被什么推翻、正确值是什么** | 只写「已作废」，等于留雷 |
| **具体数值不进记忆，写「现拉线上」** | 记忆里的字数上限过时了，AI 照旧值改，订单全挂 |
| **「我没查清」不许写成「系统做不到」** | 参数用错得到 null，写成「接口不可用」，后来被自己的错记忆挡住 |
| **自己写的注释不算规矩** | AI 把自己上次随手写的备注当成用户定的规则执行 |

### 记忆 vs 规则文件 vs RAG，放哪？

| 内容 | 放哪 |
|---|---|
| 团队共享的项目规矩 | `CLAUDE.md` / `AGENTS.md`（提交进 git） |
| 个人偏好（「回复用中文」） | 用户级规则文件 / 用户记忆 |
| 用户纠正过的做法、项目进展 | 自动记忆 |
| 大量文档、手册、历史资料 | 文件夹 + 索引（Agentic Search）或 RAG |
| 会变的数值（价格、上限、条数） | **哪都不放**，每次现查权威源 |

## 5.4 权威源优先：AI 的「真值」从哪来

ThinkNova 规定的查证顺序：

```
线上 config / 接口实时数据   ← 最高
        ▲
技术官方文档
        ▲
记忆文件                     ← 最低（只是线索，不是真值）
```

三者冲突时**以最新的线上真值为准**。AI 说「只有 / 一定 / 不可能 / 全部」这类绝对话之前，必须回源核对。

## 5.5 Hook 示例：把规则变成「一定执行」

Claude Code `settings.json` 示例（概念演示，具体字段以官方文档为准）：

```json
{
  "permissions": {
    "allow": ["Bash(npm test:*)", "Bash(git status)"],
    "deny":  ["Bash(rm -rf:*)", "Read(./.env)"]
  },
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npx prettier --write \"$CLAUDE_FILE_PATHS\"" }] }
    ],
    "SessionStart": [
      { "hooks": [{ "type": "command", "command": "git -C ~/memory pull --quiet" }] }
    ]
  }
}
```

- `PreToolUse` Hook 以退出码 2 结束 = **拦截这次工具调用**，并把错误信息反馈给模型。
- 适合做：危险命令拦截、密钥扫描（例如外发前扫 `LTAI` / `AKID` 开头的云密钥）、自动格式化、自动备份记忆。

## 5.6 行动闸门：把「规矩」变成「可检查的产物」

ThinkNova 最重要的一条认识：**AI 不缺规矩，缺的是在动手那一刻把规矩调出来。** 所以规矩不写成「要记得 X」，而写成「动手前必须先输出一行 X」——输出不出来就是没过闸。

| 闸门 | 必须先输出的产物 |
|---|---|
| 闸 0 · 开口前 | 「不可再拆的事实是 ①②③ → 推出的做法 → 我因此放弃了什么」 |
| 闸 1 · 动手前 | 「现状源：我读了＿＿，现状是＿＿」 |
| 闸 2 · 改提示词前 | 改前改后字节数（是否超上限） |
| 闸 3 · 铺开前 | 影响范围清单（改一处会波及哪些地方） |
| 闸 4 · 验收前 | 修复前基线 + 修复后同条件对比 |
| 闸 5 · 给老板拍板前 | Steelman：反方最强版本 + 我的结论 |

> 这个方法适用于所有团队：**把规则的执行结果变成可见文本，就能检查 AI 有没有真的照做。**

## 5.7 本课小结

1. 规则分四层强度，事故级规则必须落到权限 / Hook。
2. 规则文件要短、分层、指派式、带原因、不打架。
3. 记忆只留现状，旧结论当场删；会变的数值永远现查。
4. 用「可检查的产物」代替「要记得」。

**课后练习**：给你自己的一个项目写一份 `CLAUDE.md`（≤60 行），包含：命令、约定、红线、路由表四部分。
